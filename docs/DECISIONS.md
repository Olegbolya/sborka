# Журнал технических решений

> Формат: номер, дата, решение, почему, последствия. Новое решение, отменяющее старое, ссылается на него. Изменения проверок качества (`scripts/check-*.mjs`, `scripts/verify.mjs`, `.claude/`, `ci.yml`) записываются сюда **и** требуют разрешения владельца.

### ADR-001 · 2026-10-19 · Стек
Next.js (web, плеер, кабинет, редактор, админка) + NestJS (API) + BullMQ (worker) + PostgreSQL/Prisma + Redis, монорепо pnpm/Turborepo, TypeScript strict. **Почему:** тот же подход работает у BST на этом сервере; NestJS даёт агенту жёсткую структуру большого API. **Последствия:** три процесса PM2.

### ADR-002 · 2026-10-19 · DOM-рендер и артборд 390
Блоки рисуются DOM-элементами, координаты в единицах артборда шириной 390, масштаб — CSS-переменной, не `transform`. Один пакет `renderer` для редактора и плеера. **Почему:** чёткий текст, доступность, одинаковый вид в редакторе и плеере (урок BST с двумя рендерами). **Последствия:** формы сложнее прямоугольника — через `clip-path` + SVG-обводку.

### ADR-003 · 2026-10-19 · Только российские внешние сервисы
**Почему:** локализация ПД и отсутствие трансграничной передачи (`05-LEGAL.md` §2.3). **Последствия:** шрифты и библиотеки — локально; проверка `check-foreign-services`.

### ADR-004 · 2026-10-19 · Вход: VK ID, Яндекс ID, телефон
**Почему:** ст. 10 149-ФЗ в ред. 406-ФЗ; вход только по email — серая зона. **Последствия:** расходы на СМС → основной путь VK/Яндекс, длинные сеансы.

### ADR-005 · 2026-10-19 · Соседство с BST на одном сервере
Отдельные каталог, порты 3100/3110, база, пользователь БД, Redis БД 3, PM2-имена `blokum-*`, nginx-файл. **Почему:** сервер общий, BST не должен пострадать. **Последствия:** однократная подготовка сервера владельцем с sudo.

### ADR-006 · 2026-10-19 · Без отпечатков браузера
«Одна попытка с устройства» — по токену в localStorage. **Почему:** отпечаток — сбор данных об устройстве без необходимости и без согласия. **Последствия:** ограничение обходится очисткой хранилища — это приемлемо и указано в интерфейсе.

### ADR-007 · 2026-10-19 · Подсчёт результатов на сервере
Ключ правильных ответов, баллы, теги и исход колеса фортуны — только на сервере. **Почему:** честность тестов и защита от подмены. **Последствия:** запрос `check` при мгновенной обратной связи.

### ADR-008 · 2026-10-19 · Цены и лимиты в БД
**Почему:** владелец меняет тарифы без релиза. **Последствия:** `Entitlements` — единственная точка решений.

### ADR-009 · 2026-10-19 · Ворота против неполной работы
Хуки Claude Code (`SessionStart`, `Stop`), `scripts/check-*.mjs`, трассировка «требование → тест», независимое ревью каждой фазы моделью Opus. **Почему:** исполнитель — ИИ-агент; нужно автоматически ловить заглушки, пропущенные требования и ложные «готово». **Последствия:** ослабление этих проверок — только с разрешения владельца.

### ADR-010 · 2026-10-20 · Название «Блокум», домен blokum.ru
Утверждено владельцем. В интерфейсе — кириллицей (закон о русском языке), латиница — в домене. Репозиторий остаётся `Olegbolya/sborka` (рабочее имя), серверные имена — `blokum-*`, `blokum_db`, `~/blokum`. **Последствия:** при переименовании репозитория обновить ссылки в `CLAUDE.md`, `docs/prompts/*`, `docs/03-PLAN.md`.

### ADR-011 · 2026-10-20 · Универсальный движок сценариев вместо встроенных игр
По требованию владельца мини-игры придумывают пользователи. Вместо блоков-игр — правила «Когда → Если → Сделать» (TR/CN/AC), поведения (BH) и переменные (VR), исполняемые одним детерминированным движком `packages/engine/runtime`. Готовые игры — примеры-шаблоны RG-01…RG-10, собранные штатными средствами; их собираемость — приёмочный тест движка. **Почему:** свобода творчества, один код для всех механик, тестируемость. **Последствия:** результаты игр считаются на устройстве участника (RN-02, честно помечаются в кабинете); исход, влияющий на результат, — на сервере (RN-01).

### ADR-012 · 2026-10-20 · Свободные темы и шаблоны как данные
Темы, шаблоны, «Мои элементы» и библиотека — записи в БД, а не код. Системные — те же записи с `ownerId = null`, публикуются администратором. Стиль по умолчанию задаётся для каждого типа блока. Публикация сборки хранит снимок токенов темы. **Последствия:** продукт обязан работать при пустых системных коллекциях; наполнение библиотеки — задача владельца.

### ADR-013 · 2026-10-20 · Безопасность пользовательских форматов
Lottie — только через `dotlottie-web` (ThorVG, без выполнения выражений), шрифты — перекодирование в WOFF2 через HarfBuzz, SVG — только импорт контура. Открытие ссылок и копирование из сценариев — только по жесту участника. **Почему:** пользователи загружают любые файлы и собирают любую логику; нельзя дать им исполнять код или строить цепочки перенаправлений.

### ADR-014 · 2026-10-20 · Самозанятость
Владелец — плательщик НПД. Продление подписок поддерживает два режима (`AUTO` с согласием, если провайдер даёт автоплатежи самозанятым, и `LINK` — по ссылке); доход с 1 января считается в админке с тревогами у лимита 2,4 млн ₽. Приём платежей в пользу создателей при НПД не делается (агентская схема).

### ADR-015 · 2026-10-20 · Версии инструментов (P0.1)
Проверено `npm view` на 20.10.2026: Node 22 LTS, **pnpm 10.34.7** (pnpm 12 через corepack в среде агента не устанавливался), Turborepo 2.11.9, **TypeScript 6.0.3** (последняя 7.0.2, но `typescript-eslint` 8.72 поддерживает только `<6.1`), ESLint 10.13 + typescript-eslint 8.72 (правила с проверкой типов), Vitest 5.0.5 (Vite 8, преобразование через Oxc — JSX настраивается в `@blokum/config/vitest`), Next.js 16.4.2 + React 19.3.1, **NestJS 12.2 (ESM-пакеты)** — поэтому весь репозиторий на ESM (`"type": "module"`, `module: NodeNext`, импорты с `.js`), тесты Nest — через `unplugin-swc` (сохраняет метаданные декораторов), zod 4.6.7, **ioredis 5.11.1** (с ним совместим `ioredis-mock` для тестов; BullMQ 6 поддерживает ioredis ≥ 5), **Prisma 7.10.1** для P0.3 (тег `latest` у Prisma указывает на 8.0.0-rc — релиз-кандидаты не используем). `eslint-plugin-react` не подключён — не поддерживает ESLint 10; правила хуков — через `eslint-plugin-react-hooks` 7.1.1.
Пакеты собираются `tsc` в `dist/` (ESM + `.d.ts`), приложения зависят от собранных пакетов (`turbo` → `^build`).

### ADR-016 · 2026-10-20 · Drizzle ORM вместо Prisma (P0.3)
Prisma 7 при `init`/`migrate` скачивает движок схемы с `binaries.prisma.sh`, а сеть песочницы агента его не пропускает (403) — будущие сессии не смогли бы генерировать и применять миграции. **Решение:** Drizzle ORM + drizzle-kit (чистый JS, без бинарников), драйвер `pg`; миграции — SQL-файлы в `packages/db/migrations`, применяются `runMigrations()` (идемпотентно) при деплое. **Отличия от черновика §5:** итог по всем точкам доступа в `project_stats_daily` хранится с `access_point_id = ''` (вместо NULL в первичном ключе); у тарифа отдельная цена разовой покупки `price_once_rub`; колонки `legal_hold` у пользователей, сборок и медиа (под `LEGAL_HOLD` данные не удаляются); `refunded_at` у заказов; статус у журналов запросов; размеры файлов и хранилища — `bigint`; журнал аудита защищён триггерами от UPDATE/DELETE/TRUNCATE на уровне БД (AD-08); единица библиотеки ссылается ровно на один файл (CHECK). Секционирование `play_events` по месяцам — когда таблица превысит ~10 млн строк (индекс по времени уже есть). Тестовые данные (`seedDevData`) запрещены при `NODE_ENV=production`; тарифы (`seedPlans`) создаются только если их нет и не перезаписывают правки из админки.

### ADR-017 · 2026-10-20 · Раскладка на сервере и деплой релизами (P0.4, P0.5)
Вместо `dist.prev` (как в BST) — релизы: каждая выкладка собирается в новом каталоге `releases/<время>-<коммит>`, затем атомарно переключается ссылка `current`, процессы перезапускаются **по одному** с проверкой здоровья (API → `/api/v1/health`, сайт → `/healthz`, воркер → свежий heartbeat в Redis). Если проверка не прошла — ссылка возвращается на прежний релиз и процессы перезапускаются на нём (проверено локально: `SIMULATE_BROKEN_API=1` → откат за ~60 с). **Отличия от плана P0.4:** sudoers для `deploy` не нужен — nginx настраивает только `server-setup.sh`, который запускает владелец через `sudo`; деплой nginx не трогает. Данные — в `/srv/blokum`. PM2-демон общий с BST, команды — только `--only blokum-*`. Миграции выполняются до переключения и должны быть **только аддитивными** (новые таблицы и колонки); удаление/переименование — в два релиза, чтобы откат на прежний код не ломался. Пароль режима «до запуска» генерирует setup-скрипт и показывает один раз.

### ADR-018 · 2026-10-20 · Наблюдаемость (P0.6)
Новый пакет `@blokum/observability`, общий для api, web и worker: логгер pino (JSON, `service`, `version`, `requestId`), маскирование **каждой** записи и текста тревоги (телефоны, e-mail, номера карт по Луну, коды рядом со словом «код», токены в заголовках и адресах, длинные hex-строки, значения полей с «password/token/secret/cookie/otp…»), `AsyncLocalStorage` для id запроса (web `proxy.ts` → заголовок `x-request-id` → API → `runJobWithContext` в задачах воркера), класс `Alerts` с антидребезгом (ключ — не чаще раза в 10 минут) и счётчиком по окну (20 ошибок 5xx за минуту → одна тревога), каналы Telegram-бот администратора и почта (через интерфейс `Mailer`, провайдер выберет владелец), контроль диска > 80 % в воркере раз в 10 минут. Тексты тревог не содержат ПД (маскируются ещё раз перед отправкой), поэтому Telegram допустим. `/api/v1/health` всегда отвечает 200, пока процесс жив (для проверки деплоя), а состояние БД, Redis и диска — в `checks` и `status: degraded`. Ошибки API — единый формат `{ error: { code, message } }` на русском; при 5xx клиент видит только код запроса.

### ADR-019 · 2026-10-21 · Правила движка прохождения (P1.2)
`packages/engine/src/flow` — чистые функции над документом и состоянием-данными (`FlowState` хранится в сеансе). Принятые правила, которых нет в спецификации дословно:
- **Порядок «Дальше»:** сначала обязательные вопросы (только видимые: скрытые до события, скрытые условием и вложенные в скрытый контейнер не требуются), затем ветки экрана по порядку — первая выполненная решает, иначе следующий экран. Экраны, на которые ведут правила результатов, при обычном «дальше» пропускаются; после последнего — подсчёт результата.
- **Результат:** правила результатов проверяются в порядке, заданном создателем; первое подходящее побеждает (диапазон баллов включает границы; «личностный» — тег, выбранный чаще всех, ничья по `tieBreak`; «случайно» — из серверного источника). Переход на экран вида «результат» по ветке сразу завершает прохождение с результатом этого экрана (L-04 «по ветке»). Нет подходящего правила — системный экран конца.
- **Обратная связь «сразу»:** после ответа на вопрос с ключом участник видит вердикт, а ответ блокируется (`ANSWER_LOCKED`), иначе ключ можно подобрать перебором.
- **Согласие (B-20)** обязательно только тогда, когда на экране введены персональные данные (контакты или поле с пометкой имя/телефон/почта/город): без ПД согласие не нужно, принуждать к нему нельзя.
- **«НЕ» над несколькими условиями** — «ни одно не выполнено». Строки сравниваются без учёта регистра и пробелов по краям, «ё» и «е» различаются.
- **Таймер экрана:** сервер принимает «время вышло» не раньше чем за 1 с до конца (расхождение часов); при возврате на экран отсчёт начинается заново.
- **Случайность:** `RandomSource` — для всего, что влияет на результат (CN-05 с флагом, ничья), реализуется сервером; косметическая — `Rng` из seed.
- **Ключи ответов** — только у вопросов с вариантами (B-11, B-12). Для текстовых ответов, ранжирования и шкал ключа нет; правильность по ним можно задать сценарием (условие «ответ равен / содержит» → изменить переменную).
- **Подстановки в тексте:** кроме переменных (`{v}`) появились `{sys}` — «баллы», «максимум», «результат», «правильных», «вопросов» и системные переменные — и `{answer}` — ответ на вопрос (L-04, L-05). Валидатор проверяет ссылки текста на переменные и вопросы. Ветки и условия по ответам на вопросы с **прошлых** экранов больше не считаются ошибкой «блок с другого экрана» — так устроено ветвление L-02.

### ADR-020 · 2026-10-21 · Устройство движка сценариев (P1.3)
`packages/engine/src/runtime` — класс `Runtime` (`createRuntime(doc, { seed, randomSource, startedAt })`), без React, DOM и собственных таймеров: игрок передаёт события (`dispatch`), время (`tick(dt)`), рисует `views()` и выполняет возвращённые эффекты (`navigate`, `finish`, `effect`, `mediaOverlay`, `media`, `playSound`, `record`, `openLink`, `copyText`, `answer`, `warning`). Принятые правила:
- **Экземпляры блоков:** оригиналы и копии (`<образец>~<номер>`, копия контейнера копирует вложенные блоки). Копии создаются видимыми на верхнем уровне в координатах экрана, даже если образец скрыт: обычный приём — скрытый образец. «Любая копия X» (`copiesOf`) — только копии, без образца.
- **Правила:** сборки — на всех экранах, экрана и блоков — только на своём экране. Выполняются по приоритету (больше — раньше), при равном — в порядке документа. Счётчик срабатываний (CN-04) считает срабатывания триггера, включая текущее («на 5-й раз» = «равно 5»). Он и флаг «один раз» живут всё прохождение.
- **Интерпретатор** с явным стеком кадров: «Подождать» (AC-11) откладывает остаток цепочки, в том числе внутри «Повторить». Уход с экрана отменяет отложенное. «Перейти» и «Завершить» прекращают цепочку и все события до показа следующего экрана; «уход с экрана» (TR-09) при этом всё равно срабатывает, а переходы из него игнорируются.
- **SC-04:** каждое действие — шаг; больше 1000 шагов за секунду времени прохождения или больше 20 вложенных вызовов правил (через «переменная изменилась», «ответ») — правило останавливается до следующего показа экрана, эффект `warning` «Похоже на бесконечный цикл: правило «…» остановлено (…)». Счётчики для отладчика — `stats`.
- **TS-07:** ссылка и копирование выполняются только в цепочке, начатой жестом (нажатие, двойное, долгое, наведение, перетаскивание, отпускание, свайп, клавиша), и только **до** первой паузы: после «Подождать» браузер всё равно не даст открыть окно, а цепочка «жест → пауза → ссылка» выглядела бы как автоматический переход. Правила, вызванные изменением переменной, — не жест. Ссылка проверяется `SafeHref`.
- **AC-02:** значения проверяются схемой стиля (`BlockStyle.shape[…]`, `RichText`, `MediaRef`), неверные не применяются и дают `warning`. Плавно меняются числовые свойства рамки и анимируемые (`ANIMATABLE`), остальные — сразу. Новый набор эффектов/фильтров/3D сбрасывает их анимированные значения.
- **AC-04:** «случайное» для списка перемешивает его; «случайный элемент списка» берёт список из переменной, id которой указан в значении. Текст до 1000 символов, список до 500 элементов, деление на ноль не меняет значение.
- **CN-02 в браузере:** ключа ответов там нет (PL-15), поэтому «верно / неверно / баллы» работают по вердикту сервера (`setVerdict`); без вердикта — ложь.
- **TR-03:** игрок шлёт `longPress` один раз за удержание (при отпускании или на 3-й секунде), срабатывают правила с порогом ≤ длительности.
- **TR-07:** столкновение — пересечение прямоугольников в координатах экрана (без учёта поворота), через пространственную сетку 64×64 по целям каждого правила; блок не сталкивается со своими вложенными. Замер SC-05: 200 движущихся копий и 3 правила пересечений — 0,48 мс на `tick` в Node (`packages/engine/test/runtime.bench.ts`, отдельный шаг `verify` — см. ADR-021).
- **Движение для поведений** (BH-04/05, P1.9) — `setMotion(id, { vx, vy, ay })`: скорость в единицах артборда в секунду и ускорение.

### ADR-021 · 2026-10-21 · Рендерер, правило темы и язык ошибок (P1.4)
- **Стиль блока — частичное переопределение (TH-06).** `block.style` хранит только группы стиля, изменённые вручную (`StyleOverride` без значений по умолчанию; `BlockStyle.partial()` из zod 4 заполнял бы их и «своё» нельзя было бы отличить от «из темы»). Итоговый стиль — `resolveBlockStyle`: базовые значения ← стиль темы для типа блока ← свои группы ← состояние (S-15). Группа сливается целиком: редактор при правке любого поля пишет всю группу, и она становится своей. «Сбросить к теме» — `resetToTheme` удаляет группы. Цвета токенами (`{ token }`) перекрашиваются темой и внутри своих групп, HEX — нет. Движок сценариев тоже анимирует от итогового стиля.
- **Единица артборда без JS:** в плеере `--u: calc(min(100vw, 480px) / 390)`, в редакторе и миниатюрах `--u` задаётся в px; все размеры — `calc(n * var(--u))` (E-02), `transform: scale` на артборде нет.
- **Устройство блока в DOM:** `.bk-block` (позиция, размер, поворот, отражение, масштаб из сценария, прозрачность, фильтры, наложение) → `.bk-surface` (скругление, тени, свечение, размытие фона, слои заливки снизу вверх: `fills[0]` — нижний) и `.bk-content` (отступы, выравнивание текста или автораскладка, обрезка по форме, содержимое типа, текстовый слой, вложенные блоки). Вложенные блоки позиционируются от левого верхнего угла родителя. Заливка-плитка — клетки по 100 единиц × масштаб; масштаб заливки-картинки — `transform` слоя. Текст по дуге/кругу — SVG `textPath` с размером шрифта в единицах.
- **Контуры фигур, обводка по контуру и маски** добавляются в P1.6 (их задача — S-02, S-03, S-05, S-18, S-19); до неё блоки рисуются прямоугольниками со скруглением.
- **Адаптер движка** `RuntimeStore`: один `tick` за кадр `requestAnimationFrame` (шаг не больше 100 мс), изменения событий и кадров применяются пачкой, React перерисовывается только при изменениях (`useSyncExternalStore`). Нажатие, двойное нажатие и наведение мышью передаются в движок уже в P1.4; перетаскивание, свайп и долгое нажатие — в P1.9.
- **Проверка границы рендера** `scripts/check-render-boundary.mjs` (требование приёмки P1.4 в плане, утверждённом владельцем): в `apps/web` запрещены внутренние классы рендера, свои компоненты блоков/экранов, перевод стиля блока в CSS и импорт внутренностей рендера. Скрипт при каждом запуске проверяет себя на примерах. Добавлен шагом в `verify.mjs` — проверка только ужесточается.
- **Ошибки проверки данных по-русски без английских слов (N-05):** стандартная русская локаль zod печатает «array», «string» и значения перечислений, поэтому сообщения написаны в `packages/schema/src/locale.ts` («Слишком много элементов: не больше 4», «Недопустимое значение», «Лишнее поле в данных»).
- **Служебные темы** `DEV_THEMES.light/dark` — только для разработки и тестов, только системные шрифты; системные темы для пользователей наполняет владелец (TH-05).
- **Бенчмарк SC-05 — отдельным шагом `verify`.** Внутри общего прогона тестов (turbo запускает пакеты параллельно, движок — с инструментированием покрытия) замер показывал 2,3–4,7 мс вместо 0,4 мс: мерилась нагрузка соседних процессов. Бенчмарк перенесён в `packages/engine/test/runtime.bench.ts` (`pnpm --filter @blokum/engine bench`, без покрытия, файлы последовательно) и запускается в `verify.mjs` после параллельного прогона. Порог 2 мс не изменён, берётся лучший из 10 замеров по 30 тиков. Проверка не ослаблена: она по-прежнему обязательна и в CI.

### ADR-022 · 2026-10-21 · Формы, обводка и маски по контуру (P1.6)
- **Порядок задач:** P1.6 выполнена раньше P1.5 — матрица «свойство × тип блока» (P1.5) проверяет и форму, обводку, маску, которые появляются только в P1.6.
- **Произвольный контур** (`packages/schema/src/path.ts`): разбор только команд M L H V C S Q T A Z и чисел (отказ на любые другие символы, `url(`, сущности, числа больше 10⁶, больше 20 000 символов или 4 000 отрезков), перевод в абсолютные M/L/C/Z — дуги и квадратичные кривые становятся кубическими, поэтому растяжение контура на блок точное. `normalizePath` вписывает контур в 0…100; схема фигуры проверяет, что контур разбирается.
- **Контуры фигур** (`packages/renderer/src/shape/outline.ts`) строятся в единицах блока для его текущего размера. Многоугольник и звезда растягиваются на весь блок; скругление вершин — квадратичная кривая на доле `cornerRadius` от меньшего соседнего ребра. Клякса — сглаженная кривая через точки из `createRng(seed)`, вписанная по самой кривой. Облачко: тело уступает 20 % блока стороне хвостика, хвостик идёт к точке (точка внутри тела уводится к краю блока). Волна и зигзаг только по выбранным краям, внутрь блока.
- **Отрисовка:** прямоугольник, капсула и эллипс — CSS `border-radius` (тени остаются `box-shadow`). Остальные формы — `mask-image` с SVG контура на подложке и содержимом (если включена «обрезка по форме»); тени, свечение и внутренние тени таких форм — SVG-слои по контуру: растяжение через `feMorphology`, размытие `feGaussianBlur` (σ = размытие / 2), внешняя тень вырезана под блоком (на полединицы меньше контура — без шва сглаживания). Пустой SVG-фильтр делает элемент прозрачным, поэтому без размытия и растяжения фильтр не подключается.
- **Обводка у любой формы** — слой вокруг блока (на ширину обводки для «снаружи», на половину — «по центру»), закрашенный краской обводки (цвет или любой градиент, включая конический) и вырезанный маской-кольцом из SVG: «внутри» — линия двойной толщины, обрезанная контуром, «снаружи» — двойной толщины без внутренней части. Пунктир по умолчанию 3:2 толщины, точки — круглые концы с шагом 2 толщины, свой шаблон — в единицах.
- **Маски блока:** картинка по альфа-каналу (`contain`, по центру) и затухание краёв градиентами пересекаются (`mask-composite: intersect`). Маска действует на весь блок, включая тени.
- **Наклон за курсором (S-18):** в плеере блок пишет `--bk-tilt-x/y` прямо в стиль элемента (без перерисовки React), поворот — `calc((база + var(--bk-tilt-x, 0)) * 1deg)`, сила — `tiltStrength` градусов, при уходе указателя возврат в 0; у такого блока в плеере `touch-action: none` — палец наклоняет блок, а не прокручивает страницу.
- **Служебные картинки галерей** `/dev/*` рисует `scripts/dev/generate-dev-media.py` (зимний «снимок», GIF снегопада, маска-звезда) — без картинок из интернета; это не библиотека и не ассеты тем.

### ADR-023 · 2026-10-21 · Анимации, переходы, частицы и звуки (P1.7)
- **Motion 14.2.0** (MIT) — версия недельной давности (свежий выпуск вышел за два дня до начала задачи). API сверен по исходникам в `node_modules`. Motion получает только числа: планы анимаций — чистые данные (`packages/renderer/src/animation/plan.ts`, тестируются без DOM). Анимируются CSS-переменные слоя `.bk-anim` (`--bk-ax`, `--bk-as`, `--bk-ahue`…), а слой сам собирает из них `transform` и `filter` в единицах артборда. Поэтому анимация масштабируется вместе с артбордом, а свой поворот, отражения и 3D блока остаются на внешнем элементе.
- **Свои ключевые кадры** — любые свойства из `ANIMATABLE` плюс цвет заливки (`Keyframe.fill`), который накладывается слоем-тонировкой поверх заливок блока (S-04).
- **Переходы экранов** (`ScreenStage`): уходящий и приходящий экраны анимируются вместе, потом старый удаляется. Приходящий слой с первого кадра стоит в начальной точке, чтобы новый экран не мелькнул до старта Motion. Переход ветки или действия AC-05 важнее перехода экрана (T-30). Пресет ищется в теме (T-32). Медиа-переход и вставка по ответу (T-20, T-21) показываются до нового экрана, а после них экран появляется без второй анимации: мем и есть переход. Вердикт «правильно/неправильно» приходит с сервера (PL-15). Для проверок у приходящего слоя есть `data-transition`.
- **«Уменьшить движение» (T-31):** любой переход становится проявлением на 200 мс. Частицы и тряска не показываются, вспышка короче.
- **Состояния (S-15) в плеере:** наведение берётся от курсора (у пальца наведения нет), нажатие — от указателя. «Недоступно» включается, когда сценарий запретил взаимодействие (AC-18). «Выбрано», «перетаскивается» и «над зоной» приходят от движка. Отслеживаются только состояния, которые у блока заданы. Смена состояния плавная, 160 мс по прозрачности, фильтрам, цвету, скруглению и теням; `transform` не входит, потому что его ведёт движок по кадрам.
- **Частицы:**
  - Плотность считается на площадь: полный экран телефона (390 × 844) при плотности 1 вмещает 200 частиц, окно меньше — пропорционально меньше, но не меньше одной. Раньше любое окно получало те же 200 × плотность: галерея из 8 окон давала 1 120 частиц и 14–16 кадров/с на телефоне при CPU ×4.
  - Каждая форма и цвет рисуются один раз в спрайт, дальше частица — это `setTransform` и `drawImage`.
  - Плотность пикселей холста — не больше 1,5×.
  - Холст вне экрана не считает и не рисует (IntersectionObserver).
  - Итог при CPU ×4: 8 окон — 56–59 кадров/с, полный экран при плотности 100 % — 45–53 кадров/с (e2e `animations.spec.ts`, параллельный прогон).
- **Звуки** (`SoundManager`) молчат до первого нажатия или клавиши участника (правило браузеров), фон темы запускается после разблокировки. Участник может выключить звук, а включён ли он по умолчанию, решает создатель (`soundEnabledByDefault`).
- **Значок сайта** `app/icon.svg` (свой рисунок из блоков): без него каждая страница получала 404 на `/favicon.ico`, и e2e галереи ловит любые ответы ≥ 400.

### ADR-024 · 2026-10-21 · Матрица «свойство × тип блока» (P1.5)
- **Матрица** `packages/renderer/test/style-matrix.test.tsx`: 20 свойств S-01…S-20 × 22 типа × 2 служебные темы = 880 пар. Для каждой пары свойство задаётся блоку этого типа, и проверяется, что DOM изменился ожидаемо по сравнению с тем же блоком без свойства (тема по умолчанию для типа может задавать свои группы — например, скругление и тень у кнопки). Сам тест сверяет: список проверенных свойств равен S-01…S-20; список типов равен ключам `BLOCK_PROPS`; каждая группа `BlockStyle` и каждое поле блока относится к какому-то свойству (кроме id, типа, содержимого типа, вложенных блоков, поведений и правил). Проверка на прочность: если убрать из `styleToCss` один фильтр или отступы, падают ровно 44 пары соответствующего свойства.
- **S-11 у любого блока.** В спецификации медиа-настройки описаны «для блоков с медиа», а S-00 требует каждое свойство на каждом типе. Решение: у блока без своего медиа его медиа — это видеозаливка, поэтому автозапуск, звук, повтор, элементы управления, обложка и скорость блока применяются к его видеозаливкам. Раньше видеозаливка всегда шла со звуком выключенным и по кругу. Кадрирование и фокус-точка задаются у самой медиазаливки (S-04).
- **Сетка для глаз** `/dev/matrix`: 22 типа × 6 ключевых свойств (форма, градиент, обводка, тень со свечением, 3D, маска с фильтром). Строится на сервере (у вложенных блоков вопросов случайные id) и делится на экраны по 4 типа, потому что на экране не больше 100 блоков. e2e проверяет на каждом типе маску-звезду, обводку, наклон и затухание; скриншоты 390 и 1440 в обеих темах.

### ADR-025 · 2026-10-21 · Блоки (P1.8)
- **Содержимое блоков** — `packages/renderer/src/blocks/*`: медиа (B-02…B-05, B-07), вопросы (B-13…B-17, B-19, B-20) и отображение (B-08, B-09, B-22, B-23). `blockContent` по типу; у текста, фигуры, кнопки, контейнера и вопросов с вариантами своего содержимого нет — это текстовый слой и вложенные блоки. Редактор может подменить содержимое через `renderContent`.
- **Варианты ответа B-11/B-12** — самостоятельные вложенные блоки. `BlockView` даёт им роль `radio`/`checkbox`, `aria-checked`, табуляцию, нажатие и пробел; сам вопрос — `radiogroup`/`group` с именем. Выбор уходит в движок событием `answer`; «выбран» берётся из движка, а без движка — из ответов в контексте.
- **Логика в движке, а не в рендере:** «перейти сразу после выбора» (B-11) и «дальше после окончания видео» (B-04) выдают эффект `navigate: branch`. «Перемешивать» меняет местами варианты при входе на экран по зерну (косметическая случайность — после перезагрузки тот же порядок). `Runtime.currentAnswers` отдаёт ответы рендеру.
- **Таймер B-08:** движок считает в миллисекундах, блок показывает секунды (`PlayerScreen` переводит). Ошибку «1435:34» нашёл скриншот галереи; на неё есть тест на настоящем движке.
- **Дата B-17 — своё поле с русской маской** «дд.мм.гггг» / «чч:мм» / «дд.мм.гггг чч:мм» (`inputMode="numeric"`, проверка существования даты), ответ в ISO. Системное поле даты рисует формат на языке браузера («mm/dd/yyyy»), а английского в интерфейсе быть не должно. Кнопка «Календарь» открывает системный выбор через скрытое поле (`showPicker`).
- **Текст и контакты** уходят в движок после паузы 400 мс или при уходе из поля, а не на каждую букву, иначе правила «ответ изменён» (TR-12) срабатывали бы на каждый символ.
- **Lottie (B-07)** — только `@lottiefiles/dotlottie-web` 0.81.0 (MIT). Его wasm библиотека по умолчанию грузит с jsdelivr/unpkg, поэтому `apps/web/scripts/copy-vendor.mjs` кладёт его в `public/vendor/dotlottie-player-<версия>.wasm` перед `next build`/`next dev`, а рендер вызывает `setWasmUrl` до первой анимации. Если установленная версия не совпадает с `LOTTIE_WASM_URL`, сборка падает. e2e проверяет, что галерея не делает ни одного запроса за пределы сайта.
- **Доступность (PL-21):**
  - Любой блок с правилом на нажатие (и кнопка) — `role="button"`, табуляция, Enter и пробел. Кнопка «требует ответов» — `aria-disabled` и состояние «недоступно», пока на экране есть обязательные вопросы без ответа (та же проверка L-07, что в движке прохождения).
  - Alt медиа — у самого `<img>`/`<video>`; блок с подписью без своей роли — именованная `group`, потому что ARIA запрещает имя у элемента без роли.
  - Фокус с клавиатуры виден: кольцо в цвете темы, стиль только внутри артборда.
  - axe-core 4.13 по тегам WCAG 2.0/2.1 A и AA на `/dev/render-gallery`: 32 правила, 1 241 узел, 0 нарушений любой тяжести в обеих темах. На ручную проверку axe отдаёт контраст текста поверх градиентов и фото (его смотрим по скриншотам) и субтитры видео (их добавляет создатель).
- **Обводка — рамка поверх содержимого:** раньше фото и видео закрывали обводку, а с ней состояния «выбрано», «правильно», «над зоной» (нашлось в сетке состояний галереи).
- **Сетка состояний** галереи помечена `inert`: это картинка, её копии блоков не попадают в табуляцию и к скринридеру.
- **Служебные медиа галерей** — видео со снегопадом и обложкой (ffmpeg), звон бубенцов (WAV) и прыгающий снежок (Lottie JSON) рисует `scripts/dev/generate-dev-media.py`, без файлов из интернета.

### ADR-026 · 2026-10-21 · Поведения (P1.9)
- **Всё состояние поведений — в движке** (`packages/engine/src/runtime`), геометрия — чистые функции в `behaviors.ts`. Рендер только сообщает жесты и рисует.
- **BH-01 перетаскивание:**
  - Ось и границы применяет движок к каждому `dragMove`.
  - При отпускании блок притягивается только к своим зонам (если список пуст — любая зона засчитывается, но не притягивает). «Одна копия на зоне» считает занятую зону промахом. Промах с «вернуть на место» — плавный возврат в точку начала.
  - Движок принимает перетаскивание любого блока (старые сценарии P1.3 так проверялись), а плеер начинает его только у блоков с BH-01.
  - Указатель захватывается (`setPointerCapture`), у каждого блока свой палец — несколько блоков тянутся одновременно. Сдвиг больше 3 единиц — уже перетаскивание, и следующий за ним щелчок не считается нажатием.
- **BH-02 и BH-08** получают новое событие движка `pointer` (позиция пальца или курсора на экране в единицах). Экран отслеживает указатель, только если на нём есть такие блоки; палец сообщает позицию и при касании, так что от него «Нет» тоже убегает.
  - Убегание: 12 направлений, выигрывает то, что дальше от пальца, внутри области; после «сколько раз» блок больше не убегает (его можно нажать — RG-01).
  - Следование: экспоненциальное сглаживание с задержкой `lagMs`.
- **BH-03 стираемый слой:** слой — сам блок с любым оформлением. Маска — холст размером с блок (1 пиксель на единицу); кисть стирает режимом `destination-out`. Маска и доля стёртого обновляются раз в 50 мс, доля уходит в движок (TR-14), после порога слой гаснет.
- **BH-04 движение:** угол 0° — вправо, 90° — вниз; разброс и стартовая скорость берутся из зерна. Края считаются по экрану (для вложенного — по родителю): отскок, удаление, «по кругу», остановка. Контур проходится с постоянной скоростью по длине. Скрытый блок не движется, поэтому скрытый образец генератора стоит на месте.
- **BH-05 генератор** работает, пока виден; «Проиграть / Пауза» (AC-06) запускают и останавливают его, «без автозапуска» ждёт «Проиграть». Копии появляются в случайной точке области, с поведениями образца; лимит считает живые копии.
- **BH-06 колесо:** сектор выбирает `RandomSource` движка (в плеере — сервер, RN-01), секторы идут по часовой стрелке от верха в порядке списка. Поворот: не меньше трёх оборотов с замедлением, до середины выпавшего сектора под верхним указателем. В конце — эффект `wheel`, сектор становится «выбран» (CN-03), срабатывает «анимация закончилась» (TR-13). Крутит нажатие, Enter или «Проиграть».
- **BH-07 переворот** — `rotateY` 0° ↔ 180°. После ребра (90°…270°) видна обратная сторона: она заранее отражена, поэтому не зеркальная. Невидимая сторона скрыта и для скринридера. «По действию» — «Проиграть» (AC-06).
- **Производительность (SC-05)** — в три шага:
  1. Движок заменяет `anim`/`overrides` новыми объектами только при изменении, а `BlockView` кеширует стиль и CSS по ссылкам.
  2. Место из документа остаётся в `left/top`, сдвиг — свойство `translate` (без пересчёта раскладки), у движущихся блоков свой слой.
  3. Если кадр только двигает блоки, `RuntimeStore` сдвигает их элементы сам, и React экран не перерисовывает.

  Итог для 50 движущихся блоков с отскоком при CPU ×4 в песочнице без видеокарты: 39 → 45 → 52 → 58–60 кадров/с.

### ADR-028 · 2026-10-22 · Замер кадров SC-05 и доработки P1.9c
- **Где мерить.** SC-05 требует ≥ 50 к/с «на среднем телефоне (эмуляция CPU ×4)». Тест вынесен в `e2e/perf/behaviors-perf.spec.ts` и идёт в проекте `perf-390` (профиль телефона). Этот проект запускается после всех остальных тестов (`dependencies`), по одному тесту. Раньше замер шёл параллельно с соседними тестами и делил с ними процессор: на одной и той же сборке получалось от 41 до 59 к/с. Порог 50 к/с и замедление ×4 не изменились. Измерение стало точнее:
  - сначала 1 с прогрева под замедлением;
  - затем счёт кадров 3 с вместо 2.
- **Ширина 1440 в замер не входит.** Это настольный компьютер, а требование сформулировано для телефона. Без видеокарты стоимость кадра на большой ширине определяет программная композиция в браузере, а не наш код. На 1440 у нас 44–48 к/с. Основной поток при этом занят ~1,7 мс на кадр без замедления; страница из 50 голых `div` даёт те же цифры по стилю.
- **Откат обходов из a499fdd.** В нём быстрый путь `movedOnly` менял уже опубликованные объекты вида на месте. А блоки без зарегистрированного приёмника места просто не двигались. Возвращён вариант ADR-026, с одной поправкой: «только сдвиг» засчитывается, лишь если координаты правда изменились. Иначе изменился ответ или переменная, и экран перерисовывается. Без этой поправки перестал отмечаться выбор в шкале (B-15), тест `render-gallery` ловил это. Сохранена правка из a499fdd: ограничения оси и границ применяются и при отпускании (`dragEnd`).
- **Нет ухода со страницы свайпом.** Плеер ставит `html, body { overscroll-behavior-x: none }`. Иначе горизонтальный жест мимо блока браузер принимает за «назад»: участник тянет подарок или стирает слой — и покидает сборку. Так и падал BH-03 на телефоне: слой исчезал после 60 %, а следующий проход пальцем уводил страницу.
- В CI Playwright дополнительно пишет упавшие тесты аннотациями (`github`-репортёр), чтобы причину было видно без скачивания отчёта.
- **Мышь не выделяет текст** на стираемом и перетаскиваемом блоке (`user-select: none`, отмена `dragstart`). Иначе первый проход мышью выделял надпись слоя, а следующий браузер принимал за перетаскивание выделения и обрывал жест (`pointercancel`): 4 из 6 проходов терялись. Это выяснилось по самоотчёту теста BH-03 в CI.
- **Маска стираемого слоя** — на рисунке внутри блока (`.bk-scratch`), а не на самом блоке: блок ловит палец по всей площади, в том числе над уже стёртым местом.
- **`data-live` у экрана плеера** — экран ожил (обработчики навешаны, движок тикает). Разметку присылает сервер, и e2e ждут этот признак перед жестами.

### ADR-030 · 2026-10-23 · TOTP 2FA для админов (P2.6)
- **Решение.** TOTP реализован нативно на Node.js `crypto` (RFC 6238/HOTP-SHA1) без сторонних библиотек; секрет шифруется AES-256-GCM ключом `TOTP_SECRET_KEY` из env.
- **Почему.** В lockfile нет TOTP-библиотек; реализация RFC 6238 компактна (~30 строк с base32 и hotp).
- **2FA-поток.** OTP verify для ADMIN/MODERATOR с настроенным TOTP возвращает `{requiresTotp:true}` без сессии; клиент отправляет TOTP/резервный код на `/auth/otp/totp-verify`; сервер проверяет, что OTP для этого номера был использован менее 5 минут назад (запись в `otpRequests.usedAt`), затем создаёт сессию.
- **Первый админ.** `ADMIN_PHONE` в конфигурации: при входе с этим номером роль автоматически поднимается до ADMIN; факт фиксируется в audit_log.
- **Резервные коды.** 8 случайных 10-символьных hex-кодов хранятся SHA-256 хэшами в таблице `totp_backup_codes`; при использовании помечаются `usedAt`.
- **Audit log (AD-08).** Таблица `audit_log` — append-only (триггер в миграции 0001 запрещает UPDATE/DELETE). `AuditLogService` имеет только метод `log()`.

### ADR-037 · 2026-10-27 · A1: каркас редактора, черновик, автосохранение, предпросмотр (контракты для потока B)
- **Версия черновика (`revision`)** — это `number` строки `project_versions`, на которую указывает `projects.draft_version_id`. Её отдаёт `GET /projects/:id` (`draftVersionNumber`). Черновик — одна изменяемая строка; при каждом сохранении её `number` становится «следующим свободным номером проекта», так что номера не повторяются и растут.
- **`PUT /projects/:id/draft`** — тело `{document}`, заголовок `If-Match: <revision>` (допустимы `"12"` и `W/"12"`; `*` — «перезаписать что есть»). Ответ `{revision, savedAt}`. Ошибки: `428 REVISION_REQUIRED` (нет заголовка), `400 INVALID_REVISION` / `INVALID_DOCUMENT` / `DOCUMENT_TOO_LARGE` (по-русски, с путём к ошибке), `409 REVISION_CONFLICT` с `currentRevision`, `403`/`404` для чужой и несуществующей сборки. Две записи не перемешиваются: проект блокируется `FOR UPDATE` на время транзакции. Название `meta.title` копируется в `projects.title`. Лимит тела запроса поднят до 4 МБ (документ — до 3 МБ, `DOCUMENT_LIMITS.bytes`).
- **История (E-19):** при сохранении, если последний снимок старше 10 минут (или его нет), прежний черновик копируется в строку `DRAFT_SNAPSHOT`; хранится не больше 50 снимков (старые удаляются). `GET /projects/:id/versions` (снимки и опубликованные версии, новые первыми), `GET /projects/:id/versions/:versionId` (документ версии), `POST /projects/:id/restore/:versionId` — заменяемый черновик сначала сохраняется снимком, потом версия становится черновиком (`{revision, document}`). Лимит по тарифу подключится через `Entitlements` в P7.1 (сейчас единая константа `SNAPSHOTS_KEPT`). Публикационные версии пока не создаются (P5/P6).
- **Редактор (`/app/projects/[id]/edit`).** Состояние — Zustand + Immer: каждое изменение — рецепт (`lib/editor/commands.ts`), из патчей Immer строится шаг истории (до 200 шагов, ≥ 100 по E-11). Непрерывные действия — жест `beginGesture`/`endGesture` = один шаг; ввод в поле — одинаковый `mergeKey` в пределах секунды = один шаг. Холст рисуется тем же рендерером, что и плеер; поверх — слой областей выбора (перетаскивание — P3.3).
- **Автосохранение (`lib/editor/saver.ts`)** — через 1 с после правки и при уходе со страницы (`pagehide`: очередь в IndexedDB + `fetch keepalive`, если документ < 60 КБ); без сети — очередь и повтор (5 с и по событию `online`); 409 — окно «Загрузить свежую / Перезаписать» (E-18), автосохранение стоит до выбора; после перезагрузки несохранённое из очереди отправляется на своей базовой версии (устаревшая база → тот же конфликт).
- **Предпросмотр (`lib/editor/preview-session.ts`)** — настоящий рантайм сценариев (`createRuntime`) + правила прохождения `@blokum/engine` (`navigate`, `answerQuestion`, `computeResult`, таймер экрана), ничего не отправляется на сервер: прохождения не попадают в ответы, аналитику и лимиты (`isPreview`). Отладчик (SC-03): переменные с правкой «на лету» (`Runtime.setVariableValue`) и «перезапуск экрана». Журнал сработавших правил и пошаговый режим — в P3.8.
- **Исправление движка:** после `goTo`/`finish` рантайм замирал до следующего экрана — если хозяин отклонял переход (обязательный вопрос без ответа), экран оставался «мёртвым». Добавлен `Runtime.resume()`; хозяин вызывает его при отказе (тест L-07).
- **Контракт ответов участников (для потока B):** без изменений — `docs/02-ARCHITECTURE.md` §6 (`responses`: `GET /projects/:id/sessions`, …) и существующий `ResponsesService`; формат ответа в сессии — `AnswerValue` из `@blokum/engine`. Поток A уточнит его при P5.3.

### ADR-038 · 2026-10-27 · A2: холст и инспектор
- **Жесты холста** (`lib/editor/gestures.ts`) — чистые функции над хранилищем: перетаскивание, маркеры размера, поворот, рамка выделения. Всё между первым движением и отпусканием — один шаг истории (`beginGesture`/`endGesture`); рамки пишутся из состояния на начало жеста, поэтому повтор ничего не меняет. Нажатие на холсте гасит `pointerdown` по умолчанию (иначе Chromium начинал выделение текста и отменял жест) и снимает фокус с поля. Shift при перетаскивании — ось, при размере — пропорции; Alt — без прилипания (перетаскивание) и от центра (размер). Нажатие Shift *до* кнопки мыши — добавление к выделению.
- **Прилипание** (`lib/editor/snap.ts`): линии артборда (края, центр), других видимых блоков (края, центр) и сетки 8 (только когда она включена); порог 6 пикселей экрана, ближайшая линия выигрывает, при равенстве артборд и блоки сильнее сетки. Направляющие и расстояния до соседей — временный слой, в документ не попадает.
- **Группы** — `groupId` в блоках одного уровня; выбор любого члена выбирает всех (Alt — одного); копии группы получают общий новый `groupId` (`cloneWithNewIds` переписывает и `groupId`). Порядок слоёв — `z = 0…n−1` внутри уровня; панель слоёв показывает «верх — первым» и группы отдельной строкой.
- **Буфер обмена** — `localStorage['blokum.clipboard']`: блоки вместе с правилами и вложенными; координаты записываются как на артборде, поэтому вставка работает на любой экран, в контейнер и в другую сборку того же браузера; новые идентификаторы, связи внутри копии переписываются. Ссылки правил на блоки *вне* копии остаются как были (их найдёт панель ошибок, P3.7).
- **Масштаб 25–400 %** считается в пикселях на единицу (`data-unit` у холста), перетаскивание — всегда в единицах артборда. Масштаб вокруг указателя ограничен прокруткой: у самого края артборда точка остаётся под указателем не всегда (бесконечного холста нет). Два пальца: сдвиг и щипок (события `touch`); на узкой раскладке (< 961 px) страница прокручивается целиком, а жесты пальцем по холсту доработает мобильный редактор P3.14.
- **Инспектор управляется таблицей** (`lib/editor/style-specs.ts`): одна таблица описывает и интерфейс, и список ключей. Тест сверяет её с ключами `BlockStyle` и `BlockAnimation` и для каждого из 22 типов блока проверяет, что на странице есть контрол для каждого ключа при всех видах формы, заливки, краски, шрифта и необязательных частях (S-00). Пропуск контрола роняет тест — проверено намеренным удалением поля. Исключения записаны явно в тесте анимаций: ключевые кадры и контур движения (их редакторы позже).
- **Правка стиля:** группа записывается целиком в `block.style[группа]` — так она становится «своей» и не меняется при смене темы (TH-06); «Сбросить к теме» удаляет группу. В состоянии (S-15) то же идёт в `block.states[состояние]`. Значение, которое схема не принимает, не записывается. Числа: набор текстом, «протягивание» за название поля (Shift ×10, Alt ×0,1) — один шаг истории.
- **Фото в заливке:** `GET /api/v1/media/:id/file` отдаёт владельцу оригинал (тип по сигнатуре, `nosniff`, диапазоны для видео); чужой, удалённый и заблокированный файл — 404. Это **только для редактора**: публичную раздачу обработанных файлов делает P4.3 (медиадомен). В окне выбора файла можно загрузить новый; редактор читает библиотеку при открытии (`MediaCatalog`).
- **Что осталось в P3.4:** редакторы ключевых кадров (S-12, S-13, S-14) и кнопка «проиграть»; видимость по условию (S-16, вместе с условиями P3.7/P3.8); текст блока (TipTap, P3.5); шрифт — пока идентификатор вручную (библиотека шрифтов P4.6); визуальное кадрирование (S-11); перо и контур (P3.9).

### ADR-039 · 2026-10-27 · A3: каталог блоков, содержимое, экраны
- **Свойства блока управляются таблицей** (`lib/editor/props-specs.ts`), как стиль в ADR-038: `PROP_SPECS` по всем 22 видам; тест сверяет её ключи с `BLOCK_PROPS` в обе стороны. Правка идёт командой `setBlockProps`: результат проходит `BLOCK_PROPS[type].safeParse`, недопустимое (число вне границ, вариантов меньше двух) не записывается. Идентификаторы вариантов и пунктов хранит структура (`managed`), человек их не правит.
- **Варианты вопроса** — отдельные команды (`addOption`, `removeOption`, `moveOption`, `setOptionText`, `patchOption`): вариант = блок-фигура с текстом внутри вопроса + строка с баллами; перестановка меняет местами и блоки (их места на экране). В вопросе с одним ответом правильный вариант один.
- **«Добавить»** (`AddPanel`): поиск и три раздела; выбранный контейнер принимает блок внутрь, иначе — на экран под нижний блок и сверху по слоям. Контактные данные добавляются вместе с блоком согласия (B-20, PL-23). Файл из медиатеки — готовый блок нужного вида (пропорции берутся из файла, пока размеры неизвестны — 4:3). Разделы «мои элементы», «библиотека», «шаблоны экранов» появятся с P4.x/P5 (при пустых данных продукт работает).
- **Текст — TipTap 3** (`@tiptap/react`, `starter-kit`): оставлены жирный, курсив, подчёркнутый, зачёркнутый, ссылка (только `SafeHref`), два вида списков и вставка переменной/системного значения/ответа (узел `placeholder`). Заголовки, цитаты, код, разрывы строк и «хвостовой» абзац отключены — в документе их нет. Преобразование документ ⇄ редактор — чистые функции `lib/editor/rich-text.ts` (круговой тест). Правка пишет `textLayer` с `mergeKey`, слишком длинный текст (>5000) откатывается; отмена хранилища возвращает текст в редактор.
- **Панель «Экран»** (`lib/editor/screen-specs.ts`, `setScreenProps`): название, вид (обычный/вопрос/результат), высота, фон (те же слои заливки), частицы, переход на вход (8 встроенных + вставка из медиатеки), таймер экрана с переходом по окончании (L-06). Каждое значение проверяется схемой `Screen`. Не вошло: переход-пресет из темы (P3.10), шрифт подписи вставки (P4.6), ветвления и правила экрана (P3.7/P3.8), «медиа по ответу» (T-21).
- Новая переменная создаётся прямо в поле «Переменная» (имя проверяется схемой, повторы запрещены); полная панель переменных — P3.8.

### ADR-040 · 2026-10-27 · A4: логика и схема переходов
- **Один граф на валидатор и редактор.** `analyzeScreenGraph` (в `packages/schema/src/validate.ts`) строит рёбра («следующий», ветки, таймер, переходы правил, автопереходы), достижимость, экраны без выхода, круги и круги без выхода; `validateDocument` использует его же, поэтому схема в редакторе и ошибки публикации не расходятся. Круг с выходом — подсветка (жёлтая) без ошибки; круг без выхода — ошибка `ENDLESS_LOOP`.
- **Диалог «Логика»** (кнопка в верхней панели): «Схема» (SVG: колонки по числу шагов от первого экрана, возвратные рёбра пунктиром снизу, красная рамка — недостижим, жёлтая — в круге, ⚑ — конец; сводка текстом, клик по экрану — к его веткам), «Ветвление», «Результаты» (+ настройки прохождения), «Проверка» (все замечания `validateDocument` с кнопкой «Показать»: экран, блок, ветка или результат).
- **Команды логики** (`lib/editor/logic.ts`): `setBranches`, `setResults`, `setSettings` получают копию, результат проходит схему (`Screen.shape.branches`, `ResultRule[]`, `Settings`) — недопустимое не записывается, как и в ADR-039. Новая ветка берёт первый вопрос экрана («выбран первый вариант»), иначе первую переменную.
- **Редактор условий** (`ConditionEditor`) — вся схема `Condition` (CN-01…CN-06): переменная, ответ на вопрос (9 операций), состояние блока (6), число сработавших правил, случайность, группы И/ИЛИ/НЕ любой вложенности. Он же понадобится редактору сценариев (P3.8) — условия правил и действий «Если».
- **Предпросмотр** проходит ту же логику (`navigate`, `computeResult`): приёмка — личностный тест на 3 результата, три пути; ветка «налево/направо»; обоими путями.
- Не вошло: ветка с переходом-«вставкой» (`transition` в `BranchRule`) — вместе с переходами темы (P3.10); `mediaByAnswer` (T-21).
- **Подстановки в предпросмотре** (L-04, L-05): `PreviewSession.textValue` берёт текущее состояние (переменные и ответы из движка, результат) и значения `runText` движка; рамка предпросмотра передаёт его в `Artboard`. До этого `{{баллы}}`, `{{результат}}` и переменные показывались как есть.
- **Редактор текста и отмена:** поле TipTap следует за документом, читая текст из хранилища в момент эффекта (а не из свойств отрисовки, которая могла устареть, пока шёл набор) — иначе быстрый набор мог стирать последний знак.

### ADR-041 · 2026-10-27 · A4: темы
- **Тема — данные, в сборке лежит её копия** (`doc.theme = {themeId, tokens}`): правка темы на сервере не переписывает документы. Черновик забирает изменения темы при открытии редактора (`getTheme` → если токены отличаются, одна правка «Тема обновлена», дальше обычное автосохранение); опубликованная версия меняется только при следующей публикации. Ручные правки блоков (`block.style`) хранятся отдельно от темы, поэтому применение темы их не затрагивает (TH-06).
- **API** (`apps/api/src/themes`): `GET/POST /themes`, `GET/PUT/DELETE /themes/:id`, `POST /themes/:id/duplicate`, `POST /themes/:id/default`, `POST /themes/from-project/:id`, `POST /themes/from-image`. Токены проходят `ThemeTokens` (русское сообщение). Лимит своих тем «Старта» — 2 (`FREE_LIMITS.themes`, ответ 402). Тема по умолчанию — одна на владельца (`themes.is_default`, миграция 0006), новая сборка начинается с неё. Системные темы читаются и копируются всеми, менять их нельзя; список пуст, пока владелец их не опубликует.
- **Палитра из картинки на сервере**: `sharp` уменьшает до 64×64, медианное сечение (`dominantColors`) даёт до 8 цветов, `themeColorsFromPalette` назначает роли по яркости и контрасту (тёмная картинка — тёмная тема; текст ≥ 4.5 на фоне и поверхности; «основной» — самый яркий по насыщенности; «акцент» — другого оттенка), все цвета картинки остаются своими `foto_N`; мало цветов — достраиваются. Арифметика цвета (контраст WCAG, смешение, HSL) — `packages/schema/src/color-math.ts`.
- **Редактор темы** (`/app/themes`, `/app/themes/[id]/edit`): образец — документ из одного экрана со всеми 22 видами блоков, `doc.theme.tokens` которого и правится (хранилище и история те же, что у редактора сборки; `ControlEnv` даёт контролам только хранилище и медиатеку). Цвета (роли и свои), проверка контраста (предупреждение, не запрет), шрифты (системные; свои — P4.6), фон, частицы, переходы-пресеты (T-32; на экране сборки выбираются «Из темы»), декор, звуки, служебные экраны и **стиль блоков по умолчанию** теми же контролами, что инспектор (таблица `style-specs`). Автосохранение через 600 мс.
- **В редакторе сборки** — кнопка «Тема»: применить свою или готовую тему, «Сохранить оформление как тему», ссылка на «Мои темы».
- Не вошло: свои шрифты (P4.6), наборы звуков из библиотеки (P4.x), системные темы-подборка (владелец, TH-05).

### ADR-042 · 2026-10-27 · A5.1: публикация и страница плеера
- **Публикация = версия-копия.** `POST /projects/:id/publish` (и `status: PUBLISHED`): черновик проходит `ProjectDocument` и `validateDocument` — ошибки (L-08, SC-07) дают `422 PUBLISH_BLOCKED` со списком (`issues`), затем проверка ПД (PL-23); в транзакции создаётся строка `project_versions` вида `PUBLISHED` (следующий номер), `projects.published_version_id`, `published_at`, `theme_id`. Плеер читает только эту копию: правки черновика и темы доходят до участников при следующей публикации (PL-05 в смысле «обновление»). В редакторе кнопка «Опубликовать» показывает до трёх ошибок и отсылает к «Логика → Проверка».
- **Публичный API (`/play`, без сессии, `@Public`).** `GET /play/:slug` — порядок §10.3: нет/не опубликована/заблокирована → `404 «Недоступно»` (причина не раскрывается); расписание → `not_open` («Откроется … (МСК)») / `closed` (текст создателя или темы) с токенами темы, без документа; иначе `ok` с `toPublicDocument` (без ключа, баллов, меток, весов колеса, правил результатов), картой видов медиа и `indexable: false`. `GET /play/:slug/media/:id` — файл владельца только если опубликованный документ на него ссылается. `GET /play/scan/:code` — переход по QR: счётчик `opens` точки доступа и итога (`project_stats_daily`), ответ — текущий `slug` (код живёт при смене slug, PL-02).
- **Страницы.** `/s/[slug]` — серверный компонент: первый экран приходит готовой разметкой (`PlayerScreen` оживает в браузере, PL-03), дальнейшие экраны — на клиенте без перезагрузки; `generateMetadata`: og:title/description/url/type/image (абсолютный адрес картинки превью, если задана `meta.ogImage`), `noindex` (PL-05). `/q/[code]` — сервером считает переход и перенаправляет на `/s/{slug}?p={код}`. Недоступное — `404` с экраном «Недоступно»; состояния расписания — экран в теме (`StateScreen`).
- **Сессия прохождения** вынесена из предпросмотра в `lib/play/passage-session.ts` (`PassageSession`); предпросмотр — тот же класс (`lib/editor/preview-session.ts` реэкспортирует). Режим `scoring: 'server'` (плеер) не считает обратную связь и результат — публичный документ их данных не содержит (PL-15); их даёт сервер (P5.4).
- **Не вошло в P5.1:** снимок первого экрана как запасная картинка превью (нужен серверный рендер в картинку — отдельным решением), свой slug на платных тарифах (P7.1).

### ADR-043 · 2026-10-27 · A5.2: проверки доступа, лимиты, старт прохождения
- **Старт** — `POST /play/:projectId/sessions`: проверки §10.3 по порядку (сборка → расписание → лимиты создателя → пароль → «18+»), затем допуск в транзакции под блокировками: сначала `pg_advisory_xact_lock` по аккаунту, потом по сборке (порядок один и тот же — сборки одного аккаунта не блокируют друг друга намертво). Под замком проверяются: лимит начатых (`limit_counters.STARTS`), лимит завершённых, месячный лимит тарифа (PL-07, `FREE_LIMITS.passesPerMonth`, считаются сессии этого аккаунта за календарный месяц UTC, предпросмотры не в счёт), «одна попытка» (PL-10), затем создаётся `participant_sessions` и растёт `STARTS`.
- **Атомарный счётчик — PostgreSQL, а не Redis + Lua** (отступление от формулировки плана): `limit_counters` уже источник истины и в кабинете («37 из 50»), замок на строку/сборку гарантирует, что наплыв не превышает лимит (тест: 200 одновременных стартов при лимите 50 → ровно 50; для завершённых 60 → 20), сверка с БД не нужна. Redis + Lua можно добавить, если замок на сборку станет узким местом — интерфейс `start` не изменится.
- **Лимит завершённых.** Незавершённое прохождение занимает место до суток без действий (`ACTIVE_WINDOW_MS`), иначе завершённых могло бы стать больше лимита; старое брошенное место освобождается.
- **Пароль (PL-08)** хранится только хэшем scrypt (`settings.passwordHash`); кабинет получает `hasPassword`, ни текст, ни хэш не возвращаются (ни в `access-settings`, ни в `GET /projects/:id`); пустая строка снимает пароль. Допуск — HMAC от проекта и текущего хэша пароля (`x-play-unlock`): смена пароля обесценивает прежние допуски. Вход — `POST /play/:slug/enter`; перебор: 10 неверных за 10 минут с одного адреса → 429 (счётчик в памяти процесса; общие лимиты частоты — P9.4).
- **«18+» (PL-09)** — `settings.age18`; подтверждение декларативное (`enter {age18: true}` и заголовок `x-play-age`); до подтверждения документ не отдаётся ни в разметке, ни в API. **Пароль и «18+» стоят до документа**: страница отдаёт только состояние с темой.
- **«Одна попытка» (PL-10)** — токен устройства (`localStorage`, случайный `randomUUID`), на сервере только `sha256(project + token)`; отпечатков нет (TS-12), `ip_hash` не заполняется. Без токена при включённой опции — 400.
- **Настройки доступа:** очистка поля в кабинете отправляет `null` (раньше пропавшее поле не стирало сохранённое значение); новые поля `maxStarts`, `age18`.
- **Публикация** проверяет сведения об операторе до схемы документа (как и раньше, ПД-ошибки первыми); тесты `legal` теперь кладут в черновик допустимый документ — публикация не принимает документ, не прошедший схему.
- Не вошло: уведомление создателю о месячном лимите (P6.7).

### ADR-044 · 2026-10-27 · A5.3: прохождение и ответы
- **Сессия — на сервере, идентификатор — «ключ» участника.** `participant_sessions` создаётся при старте (ADR-043); 16 случайных знаков хранятся в `localStorage` (`bk:session:{projectId}`) и дают доступ к своей сессии: `GET /play/sessions/:id` (продолжение: место, переменные, ответы, **версия, с которой начато** — новая публикация текущее прохождение не ломает), `POST …/answers`, `POST …/check`, `POST …/branch`, `PUT …/state`, `POST …/complete`. Перезагрузка продолжает ту же сессию, второй не создаётся (тест: одна сессия в кабинете).
- **Ответ (PL-12, PL-13).** Сервер проверяет его тем же `normalizeAnswer` движка по **полному** документу (чужой вариант, лишние варианты, неверный тип — 422 по-русски). Идемпотентность: `clientEventId` (уникален в сессии) и `clientTs` — повтор события ничего не меняет, более старое не затирает новое (миграция 0007). «Сразу» и вопрос с ключом: ответ окончательный (409 `ANSWER_LOCKED`). Время на экране и экран пишутся (PL-14).
- **Карты (TS-10).** `looksLikeCardNumber` (движок): 13–19 цифр подряд или группами через пробел/дефис + Луна, на любых соседних группах (ловит «карта 4111 1111 1111 1111 12»); применяется в `normalizeAnswer` для текстов и контактов — то есть **и в браузере, и на сервере**; отклонённое не сохраняется нигде, создателю остаётся событие `CARD_LIKE_REJECTED` без текста (`play_events`).
- **Ключ не уходит клиенту (PL-15).** Обратная связь «сразу» — `check`: ответ только для уже отвеченного вопроса и только в этом режиме; итог — `complete`: баллы, правильные, результат (правила результатов, включая «по ветке»: экран вида «результат», на который не указывает ни одно правило) считает движок из ответов в БД; повтор возвращает то же, завершение считается один раз (`COMPLETIONS`, условный `UPDATE`). Ветки экрана, читающие ключ (`correct/wrong/scoreGte/scoreLte`), решает сервер (`branch`), остальные — клиент.
- **Очередь отправки (PL-12)** — `PlayClient`: ответы, состояние и конец идут через очередь в `localStorage` (`bk:outbox:{session}`), переживающую перезагрузку; повтор после обрыва с нарастающей паузой и по событию `online`; отказ 4xx (кроме 408/429) окончателен, человеку — сообщение; состояние склеивается до последнего.
- **Лимиты частоты (TS-13):** старты — по хэшу адреса (`sha256(день + адрес)`, адрес не хранится; по умолчанию 120 в час, `PLAY_STARTS_PER_HOUR_PER_IP`), ответы — 240 в минуту на сессию. Невидимая SmartCaptcha при аномалиях ждёт ключей владельца. В e2e лимит старта отодвинут (все участники с одного адреса), его проверяет тест API.
- **Движок и рендерер (исправления, найденные плеером):** тексты с `{{переменная}}` и `{{ответ}}` перерисовываются при смене значения (раньше обновлялись только блоки «значение» — L-05 в плеере и в предпросмотре); `RuntimeStore.dispatch` передаёт владельцу и ответ, который дал сам участник (раньше только ответы от правил), поэтому «сразу» работает от нажатия.
- **Публичный документ не знает правил результатов**, поэтому `PassageSession` в режиме `server` помечает экраны вида «результат» как цели, которых «дальше» не касается, и заканчивает прохождение на сервере; явный `goTo` на экран результата тоже заканчивает его (результат — серверный, экран остаётся).
- **«Одна попытка» и продолжение:** завершённое прохождение при включённой опции больше не показывается — «Вы уже проходили»; кнопка «Пройти заново» (стирает ключ сессии) остаётся, где опции нет.
- Не вошло в P5.3: невидимая капча (ключи владельца); значения игр и правдоподобие (P5.4).


### ADR-045 · 2026-10-27 · A5.4: честная случайность и значения с устройства
- **Исход колеса и случайных чисел (RN-01).** `POST play/sessions/:id/random {sourceId, seq}`: сервер тянет исход по весам (колесо) или число (общий поток `main`), записывает его в `random_draws` и отдаёт по порядку `seq` — повторный запрос того же `seq` возвращает ту же запись, пропустить номер или «перетянуть» нельзя. Веса секторов в публичный документ не попадают. Клиент (`ServerDraws`) берёт исходы вперёд (по одному на колесо, 8 для общего потока) до анимации; без сети движок крутит своё и это помечается «на устройстве».
- **Значения игр (RN-02, AC-14, VR-04).** `POST play/sessions/:id/values`: проверяются тип и диапазон переменной, скорость роста, лимит 50 названий и карты (TS-10); принятые пишутся в ответы с `deviceReported` — кабинет показывает «посчитано на устройстве». Ничья (CN-05) решается по 32 записанным числам сервера.
- Движок: `spinWheel(…, drawn)` и `RuntimeOptions.drawWheel` позволяют подставить сектор сервера; без них поведение прежнее.

### ADR-046 · 2026-10-27 · A5.6: безопасность участника
- **Подвал и знак (PL-16, TS-11).** В плеере на каждом экране закреплён подвал «Создано пользователем · Пожаловаться»; «Пожаловаться» не убирается ни на одном тарифе. Водяной знак «Сделано в Блокуме — создать свою» показывается, если `Entitlements.watermark` (на «Старт» — да); сервер отдаёт `watermark` и `ad` в ответе `/play/:slug`.
- **Жалоба.** `POST /reports` (публичный, без сессии): категория из `REPORT_CATEGORIES` (`@blokum/schema`, коды §2 простыми словами, приоритет P0/P1/P2 по §4.2), описание 5–4000 знаков, контакт необязателен и только с согласием. В `reports` пишутся снимок **опубликованной версии** (`snapshot_version_id`), срок (`sla_due_at`: P0 — 1 ч, P1 — 24 ч, P2 — 72 ч) и хэш адреса (с дневной солью, сам адрес не хранится). Капчи пока нет (ключи у владельца) — вместо неё ограничение 5 жалоб в час с адреса (`REPORTS_PER_HOUR_PER_IP`, в e2e отодвинуто, как TS-13). **Не вошло:** автоснятие по P0 и тревога владельцу, очередь в админке — P9.3.
- **Подпись под полем (PL-17).** `TextInputContent` в режиме плеера: колонка «поле + мелкая подпись»; в редакторе подписи нет.
- **Реклама (PL-18).** `PATCH /projects/:id/advertising` (`advertiser` 2–200 знаков, `erid` латиница и цифры 4–64, `inn` 10 или 12 цифр, пустое тело — выключить) пишет `projects.is_advertising/ad_marking`; плеер закрепляет полосу «Реклама · рекламодатель · ИНН · erid: …». Переключатель — в настройках сборки кабинета. Передача данных в ЕРИР через ОРД — P8.
- **Безопасный переход (PL-22, TS-12).** Ссылки текста (`RichTextView`) и действие «открыть ссылку» (AC-16) ведут на `/out?u=…`: страница показывает адрес и предупреждение, переход — только по нажатию «Перейти», `noopener noreferrer nofollow ugc`, `referrer: no-referrer`, `noindex`. Допустимы `http(s)` без логина в адресе, `mailto`, `tel` (как `SafeHref`); остальное — «Эту ссылку открыть нельзя». Действие AC-16 открывает `/out` в новой вкладке сразу в обработчике жеста; «скопировать текст» (AC-17) пишет в буфер.
- Попутно: вкладки кабинета сборки переносятся на узком экране (раньше страница шире 390 px), ошибки кабинета читают `error.message` ответа API.

### ADR-047 · 2026-10-28 · A6: вход админа через VK ID / Яндекс ID с обязательным TOTP
- **Первый администратор — по аккаунту провайдера:** `ADMIN_ACCOUNTS=vk:<id>,yandex:<id>` (регистр не важен). При входе такой аккаунт получает роль `ADMIN` (запись `ROLE_ADMIN_BY_ACCOUNT` в аудите); `ADMIN_PHONE` остаётся для входа по телефону (ADR-033). Поиск пользователя по входу теперь учитывает провайдера: одинаковый номер у VK и у Яндекса — разные люди (раньше совпадение по одному номеру пускало бы в чужую запись).
- **Второй фактор до сессии.** Для `ADMIN` и `MODERATOR` обратный вызов провайдера не создаёт сессию: ставит подписанную метку `bk_mfa` (HMAC от `TOTP_SECRET_KEY`, 10 минут, `HttpOnly`, путь `/api/v1/auth/oauth`) и ведёт на `/login/2fa`. `POST /auth/oauth/mfa/start` — что нужно (код или первая настройка), `POST /auth/oauth/mfa/verify {code}` — проверка кода приложения или резервного кода; после неё выдаётся сессия. Метка не годится как сессия. Пять неверных кодов за 10 минут — 429.
- **Первая настройка без «висящего» секрета:** секрет создаётся при `start`, лежит зашифрованным только в метке и сохраняется в `users.totp_secret_enc` после первого верного кода; тогда же выдаются 8 резервных кодов (один раз). Брошенная настройка ничего не блокирует (в старом пути через кабинет секрет сохранялся до подтверждения).
- В аудит пишутся `TOTP_CONFIRMED`, `TOTP_LOGIN`, `TOTP_LOGIN_BACKUP`, `TOTP_FAILED`.
- **e2e:** `scripts/e2e-api.sh` назначает администраторами четыре номера эмулятора (`7000000000{01..04}`, по два на проект Playwright) и перед запуском стирает их записи, чтобы настройка шла с нуля. Сквозной тест `golden-path.spec.ts`: войти → добавить вопрос в редакторе → опубликовать → пройти без входа → ответ в кабинете → CSV/XLSX.
- **Не вошло:** страницы админки (P9.3), перенастройка секрета у админа из кабинета, переключатель эмулятора на настоящие VK ID / Яндекс ID (ждёт ключей владельца).

### ADR-048 · 2026-10-28 · P5.7 и P5.5: бюджет скорости плеера и три браузера
- **Бюджет (PL-19, N-02, SC-05).** Плеер участника весил 306 КБ JS (gzip) при бюджете 250: 134 КБ из них — разборщик схем `zod`, который тянули `resolveBlockStyle`, проверка значений свойств в движке и общий вход пакета. Теперь плеер не содержит `zod`: **210,7 КБ**, Lighthouse mobile Performance 97–99, LCP 0,6–0,8 с, игра из 50 движущихся шариков при CPU ×4 — 56,9 кадра/с.
- **Как убран `zod` из плеера.** (1) `@blokum/schema`, `engine`, `renderer` помечены `sideEffects: false` — модули, которые никто не использует, не попадают в сборку; установка русских сообщений `zod` (`locale.ts`) выполняется там, где `zod` нужен, — отдельный вызов не требуется. (2) Всё, что читает плеер, вынесено в модули без `zod`: `walk.ts` (`walkBlocks`), `plain-text.ts`, `href.ts` (`isSafeHref`), `scenario-limits.ts` (`SCENARIO_LIMITS`, `GESTURE_TRIGGERS`), `color-roles.ts` (`DEFAULT_COLORS`), `frame-values.ts`. Публичный вход пакета тот же. (3) `resolveBlockStyle` больше не разбирает стиль схемой: группы, которые есть у блока, темы и состояния, уже разобраны при записи (TH-06), недостающие берутся из `BLOCK_STYLE_DEFAULTS` (готовое значение `BlockStyle.parse({})`); результат — свежие копии, как и раньше. Тесты: значение равно разбору пустого стиля; на 300 случайных наборов групп результат равен `BlockStyle.parse` слияния. (4) Тема «по умолчанию» рендерера записана готовым значением (`DEFAULT_RENDER_TOKENS`, тест равенства со служебной светлой темой); `DEV_THEMES` помечены `/*#__PURE__*/`. (5) После `tsc` в `@blokum/schema` скрипт `scripts/annotate-pure.mjs` помечает объявления схем знаком `/*#__PURE__*/`.
- **Значения «Изменить свойство» (AC-02) проверяются при публикации, а не в плеере.** `parseSettableValue` (`@blokum/schema`) — те же схемы, что раньше были в движке. Новая ошибка публикации `INVALID_PROPERTY_VALUE` («Значение для свойства … не подходит»). `RuntimeOptions.parseValue` — необязательная проверка значений `style.*`, `textLayer`, `props.media`: её передают предпросмотр редактора (`PreviewSession`) и тесты движка; плеер принимает опубликованный документ как проверенный, размер, положение и отражение проверяет всегда (`parseFrameValue`).
- **Измерение.** `e2e/perf/player-budget.spec.ts` (проект `perf-390`, боевая сборка, три эталонные сборки: простая анкета, сборка с правилами, игра): JS страницы участника gzip ≤ 250 КБ, LCP < 2,5 с при сети 4G и CPU ×4, у игры ещё ≥ 50 кадров/с. `e2e/perf/lighthouse.spec.ts`: Lighthouse (`lighthouse` как devDependency) по тем же страницам, Performance ≥ 85, LCP < 2,5 с. Обе проверки идут в основном E2E-job.
- **GS-01 и GS-02.** Сквозные сценарии `golden-ded-moroz` и `golden-own-game` планом назначены на конец фазы 6 и ещё не написаны; пока вместо них три сборки того же вида (анкета, правила и переходы, 50 объектов с поведением). Когда сценарии появятся, их страницы добавить в оба спека.
- **Не вошло в P5.7:** ленивая подгрузка движка сценариев. Бюджет выполнен без неё, а `PassageSession` строит рабочую среду синхронно (первый экран делается на сервере) — ленивая подгрузка потребовала бы переписать запуск плеера. Вернуться, если бюджет станет тесным.
- **Три браузера (PL-20, P5.5).** Новый workflow `.github/workflows/browsers.yml` (в `ci.yml` не трогали): Firefox (компьютер, 1440) и WebKit (профиль iPhone, 390) проходят эталонные сценарии плеера — `play`, `play-session`, `play-safety`, `behaviors`, `animations`, `shapes`, `matrix`, `render-gallery`, `artboard`. Проекты `firefox-1440` и `webkit-390` в `playwright.config.ts` существуют только при `PW_BROWSERS=all`: основной E2E ставит один Chromium. Снимки сравнения (`visual.spec`) остаются только у Chromium. Первый прогон показал: все эталонные сценарии плеера проходят и в Firefox, и в WebKit, кроме галереи анимаций `animations.spec`: в Firefox не работают два замера кадров (замедление процессора идёт через CDP, он есть только в Chromium) — они пропускаются вне Chromium; в WebKit (сборка Playwright для Linux) значения анимируемых переменных не меняются и страница не становится «устойчивой» (S-12, S-13, S-14, T-30) — галерея исключена из `webkit-390`. **Это открытый дефект:** проверить анимации на настоящем Safari (iPhone), см. «Осталось» в PROGRESS. Яндекс Браузер и Samsung Internet — на движке Chromium, встроенные браузеры Telegram и VK — на WebView тех же движков: отдельной проверки нет.

### ADR-049 · 2026-10-28 · P9.3: админка модерации и контента
- **Состав.** API `/admin/*` (`apps/api/src/admin`, роли `MODERATOR` и `ADMIN`; выключатели, состояние, аудит, системные шаблоны и темы — только `ADMIN`) и страницы `/admin/*` на сайте: главная, очередь жалоб, случай, обжалования, пользователи и профиль, заявления и требования, шаблоны и темы, выключатели, состояние, журнал аудита. Доступ проверяется на каждом запросе API; страницы лишь прячут лишнее.
- **Решения (AD-03).** `POST /admin/actions {targetType, targetId, action, reasonCode, note, reportId?}`: цели — сборка, файл, пользователь; действия по `ACTIONS_BY_TARGET` (`@blokum/schema`); причина из списка шаблонов `MODERATION_REASONS`, комментарий 3–2000 знаков. В одной транзакции: изменение объекта, запись в `moderation_actions` (с состоянием «до» в `details.previous`), запись в `audit_log`, закрытие жалобы. Владельцу — сообщение (`notifications`, плюс письмо через `EmailSender.sendNotice`, если адрес подтверждён). Для `BLOCK_USER` категории A текст без подробностей. `LEGAL_HOLD`/`RELEASE_HOLD` владельцу не сообщаются. `RESTORE` возвращает состояние до **первого** из действующих решений: автоснятие, затем блокировка, затем восстановление — сборка снова в публикации.
- **Автомеры (§4.2).** `ReportsService` после приёма жалобы зовёт `ModerationService.onReport`: категория P0 или три независимых жалобы (разные хэши адреса) за час на одну сборку → жалоба становится P0, опубликованная сборка снимается (`UNPUBLISH`, автор решения `system`, причина `AUTO_P0`), поднимается критическая тревога. «Жалоба не подтвердилась» отменяет автоснятие, если других открытых жалоб нет.
- **Обжалование.** Создатель: `GET /projects/:id/moderation`, `POST /projects/:id/appeals` (10–2000 знаков; одно открытое обращение на решение; для снятых с публикации то же обращение — «Исправил — проверить снова»). Рассматривает другой модератор; тот, кто принял решение, — не раньше чем через 24 часа (`APPEAL_SELF_REVIEW_HOURS`). Удовлетворить = `RESTORE`; отказ — сообщение создателю. Таблицы `appeals`, `notifications`, поля `reports.assignee_id`, `moderation_actions.details` — миграция 0008.
- **Выключатели (AD-07).** `FeatureFlagsService`: чтение из базы не чаще раза в 30 с, по умолчанию включено; для выключения нужна причина; каждое переключение — аудит и тревога владельцу. Закрывают: регистрацию (первый администратор из `ADMIN_ACCOUNTS`/`ADMIN_PHONE` входит всегда), загрузку файлов (обычную и по частям), публикацию, плеер (все сборки и продолжение прохождений отвечают «Недоступно»), СМС. `GET /flags/public` отдаёт `externalLinks` и `player` сайту.
- **Заявления и требования (AD-04).** Регистры `copyright_claims` (срок 24 часа, одно уточнение, снятие материала = решение по сборке/файлу с причиной B6, счётчик снятий по сборке) и `authority_requests` (действия, закрытие только после записанного действия). Публичных форм подачи заявления здесь нет — записывает сотрудник.
- **Состояние (AD-09).** Базa, Redis, диск, очередь обработки файлов (по записям в БД: ждут, застряли >10 минут, отклонены за сутки), последняя резервная копия из `BACKUP_DIR`, работа, ждущая людей. Журнал `GET /admin/audit` с фильтрами.
- **Системные шаблоны и темы (AD-11).** Из сборки (черновик, иначе опубликованная версия) копируется документ; тема — из темы создателя или из темы внутри сборки, копией. Категория, порядок, обложка; снятие — `deleted_at`. Профиль автора в админке даёт кнопки «как системный шаблон» и «тему сборки — системной».
