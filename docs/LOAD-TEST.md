# Нагрузочный тест плеера (N-02)

**Требование N-02:** запросы плеера отвечают быстрее 300 мс у 95 % обращений (p95) при 200 одновременных участниках на домашнем сервере.

## Что проверяется
Сценарий `infra/load/play.js` (k6) ведёт каждого участника так, как это делает плеер: открыть страницу сборки → начать прохождение → ответить на каждый вопрос → сохранить место на каждом экране → завершить. Между шагами пауза 1–3 секунды. Участники делятся поровну между тремя эталонными сборками (их создаёт и проходит тест `e2e/load-reference.spec.ts`):

| Сборка | Что внутри |
|---|---|
| Эталон: викторина | два экрана, два вопроса с ключом |
| Эталон: анкета | текстовый ответ и вопрос с несколькими вариантами |
| Эталон: информация | два экрана без вопросов |

Пороги теста: `player_request_ms p(95) < 300`, доля ошибок запросов < 1 %, ни одного сорвавшегося прохождения.

## Результат на локальном стенде (10.11.2026)
Стенд: песочница агента (API NestJS + PostgreSQL 16 + Redis на одной машине), 200 участников: набор 30 с, удержание 2 мин, тариф «PRO» у автора, лимиты запусков с одного адреса подняты.

| Показатель | Значение |
|---|---|
| Запросов плеера | 27 405 |
| Прохождений завершено | 4 563, сорвалось 0 |
| Ошибок запросов | 0,00 % |
| Среднее время ответа | 12,5 мс |
| p90 / **p95** | 24,9 мс / **35,1 мс** |
| Самый медленный запрос | 211 мс |

Это показывает, что код и сценарий укладываются в порог с большим запасом. **Требование N-02 считается выполненным только после замера на домашнем сервере** — там другое железо, соседний BST и сеть.

## Как провести замер на сервере (окно согласует владелец)
1. Владелец называет окно (лучше ночью по Москве, 30 минут).
2. Агент готовит три эталонные сборки на blokker.ru от аккаунта владельца с тарифом, где хватает прохождений (нужно около 5 000, «PRO» даёт 10 000 в месяц), и временно поднимает лимиты запусков с одного адреса: `PLAY_STARTS_PER_HOUR_PER_IP=1000000`, `PLAY_ANSWERS_PER_MINUTE=1000000` в `infra/server.env` (деплой). Все 200 участников идут с одного адреса раннера GitHub, иначе защита от накрутки (TS-13) их остановит.
3. Владелец открывает на GitHub: **Actions → Нагрузочный тест → Run workflow**, вписывает адреса трёх сборок и нажимает зелёную кнопку. Тест идёт ≈ 3 минуты; до и после проверяется здоровье Блоккера (`/api/v1/health`) и BST (`https://mybst.ru/`).
4. Агент возвращает лимиты на прежние значения, удаляет тестовые прохождения (они считаются в аналитике), записывает результат в этот файл.

Локальный запуск: `pnpm build`, затем `LOAD_SLUGS_FILE=/tmp/slugs.txt pnpm exec playwright test e2e/load-reference.spec.ts`, API с поднятыми лимитами (`PLAY_STARTS_PER_HOUR_PER_IP`, `PLAY_ANSWERS_PER_MINUTE`) и `k6 run -e BASE_URL=http://127.0.0.1:3100 -e SLUGS=$(cat /tmp/slugs.txt) infra/load/play.js`.
