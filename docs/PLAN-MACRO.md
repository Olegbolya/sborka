# План по макрозадачам (экономный режим)

> Рабочий план. Один макрошаг = одна сессия Claude Code (или несколько, если макрошаг разбит на подшаги).
> Подробные «Сделать / Приёмка / Тесты» каждой задачи `Pn.m` остаются в `docs/03-PLAN.md` — **не читай его целиком**, бери только нужный раздел (команды ниже).
> Модель по умолчанию — **Sonnet**. **[OPUS]** — только где отмечено, и только если Sonnet дважды не справился.

## ⚡ Этап MVP — 7 дней, 23–30 октября (решение владельца, ADR-032)

**Цель MVP — первая рабочая версия.** Создатель:
- входит;
- в редакторе собирает сборку из основных блоков, с переходами и баллами;
- публикует ссылку и QR.

Участник проходит сборку без регистрации, а создатель видит ответы в кабинете и выгружает их.

**После MVP — сразу полная реализация.** Каждая задача `Pn.m`, сделанная в MVP частично, остаётся 🟨 и доделывается до конца по `03-PLAN.md`. Ничего из полного плана не отменяется.

**Правила MVP**
- Это **меньше функций, а не хуже код**. Все жёсткие правила `CLAUDE.md` действуют: без заглушек, тесты, `pnpm verify`, зелёный CI.
- Что вошло в MVP, сделано целиком; чего нет — того нет в интерфейсе, а не «кнопка без действия».
- Статус задачи, сделанной в MVP частично, — 🟨. В «Заметках» PROGRESS — две строки: «MVP: сделано …» и «Осталось после MVP: …». Строки TRACEABILITY — только для ID, которые реализованы полностью.
- Два потока работают параллельно, каждый в своих ветках `a/…` и `b/…`. В `main` вливаются небольшими кусками после зелёного CI: `git pull --rebase` → push.
- **Миграции базы (`pnpm db:generate`)** — сразу после `git pull` и сразу в `main`, чтобы номера миграций не столкнулись.
- **Общие контракты** (API ответов, модель `Project`/`Submission`) поток A фиксирует в `02-ARCHITECTURE.md` / ADR в первый день. Поток B строит по ним.

## Как работать и не тратить лимиты

1. **Начало сессии:** `docs/PROGRESS.md` → строка 🟨 (или первый ⬜) → найди её макрошаг здесь. Больше ничего не читай заранее.
2. **Читай кусками, а не файлами:**
   - задача: `grep -n -A14 "^### P3.4 " docs/03-PLAN.md`
   - требование: `grep -n "\`S-04\`" docs/01-PRODUCT-SPEC.md` (так же для `05-LEGAL.md`, `06-TRUST-SAFETY.md`)
   - код: сначала Grep по имени, потом Read с `offset/limit`. Большие файлы (`runtime.ts`, `BlockView.tsx`, `style-matrix.test.tsx`) целиком не открывать.
3. **Тесты по месту:** во время работы — только затронутый пакет и файл: `pnpm --filter @blokum/renderer exec vitest run test/x.test.tsx`. `pnpm verify` — **один раз** перед коммитом. Вывод всегда обрезай: `… 2>&1 | tail -40`.
4. **e2e (Playwright) локально НЕ запускай** — их гоняет CI на GitHub (см. «Работа на Windows» ниже). Свои e2e пиши, проверь `pnpm -s typecheck:e2e`, а результат смотри в CI.
5. **Скриншоты:** только в конце макрошага, просмотреть Read'ом **не больше 4** (390 светлая, 1440 тёмная, редактор 1024 — где есть интерфейс). Остальное сторожат `toHaveScreenshot` из P1.10.
6. **CI:** после push — один раз `gh run watch -R Olegbolya/sborka --exit-status`; не опрашивать в цикле.
7. **Учёт коротко:** PROGRESS — доказательство в 1–2 строки (команда + итог); все `Pn.m` макрошага получают ✅ с одним хэшем; в TRACEABILITY по строке на каждый ID (этого требует `check-progress`), без пересказа.
8. **Контекст:** `/compact` после каждого коммита, `/clear` между макрошагами. Никаких субагентов.
9. **Если не влезает:** закончи текущий подшаг целиком, `main` зелёный, запиши в PROGRESS «Заметки» точное место остановки, `/clear`.

## Работа на Windows в VS Code (Claude Code) — чтобы не было долго

Владелец работает в Claude Code в VS Code на Windows. Ниже обязательные правила.

1. **Не запускай `pnpm e2e`, `pnpm build && pnpm e2e`, Playwright, Lighthouse, k6 и замеры кадров.**
   - Причины: на Windows они идут десятки минут, зависают на браузере, а цифры скорости там бессмысленны.
   - Источник правды — задание «E2E (Playwright)» в CI.
   - Упавший тест читай по аннотациям: `gh run view <id> -R Olegbolya/sborka`. Если не видно — `gh api repos/Olegbolya/sborka/check-runs/<job_id>/annotations --jq '.[].message'`.
2. **Скорость не меряй на `pnpm dev`.** Режим разработки в разы медленнее сборки. Скорость меряет только CI (`e2e/perf/*`, проект `perf-390`).
3. **Визуальные эталоны (`e2e/__visual__`) не снимай локально** — у тебя другой браузер, и картинки не совпадут с CI.
   - Если намеренно меняешь внешний вид галерей, запушь ветку `visual-baselines/<что-меняется>`: workflow сам переснимет эталоны и закоммитит их в эту ветку.
   - Потом посмотри изображения и влей ветку.
4. **Тяжёлые команды — один раз и с обрезанным выводом.** `pnpm verify 2>&1 | tail -40` — только перед коммитом, не после каждой правки. Во время работы — тесты одного пакета или файла.
5. **Не жди молча.**
   - Если команда идёт больше 5 минут без вывода — прерви её, напиши владельцу одной строкой, что делаешь и на чём застрял.
   - Не повторяй одно и то же исправление по кругу: после двух неудачных попыток остановись, опиши причину и варианты.
6. **CI ждать — один раз.** `gh run watch <id> -R Olegbolya/sborka --exit-status`, без циклов опроса.
7. **Пути и окончания строк.** В скриптах — пути через `node:path`, никаких `/tmp` и `rm -rf` в инструкциях. Файлы — с LF (CRLF ломает проверки; `git config core.autocrlf false`).
8. **Тесты на плеер ждут, пока экран оживёт:** `.bk-player-screen[data-live="true"]` (разметку присылает сервер, обработчики появляются позже).
9. **Что отдавать облачной сессии Claude (не делать здесь).** Если задача упирается в Playwright, скорость, визуальные эталоны или тест, который падает только в CI, — не трать лимиты. Запиши в PROGRESS «Заметки», что нужно, и сообщи владельцу.

**Владельцу — для скорости:**
- в начале сессии включи режим авто-принятия правок (Shift+Tab);
- на частые команды (`pnpm`, `git`, `gh`) отвечай «Yes, and don't ask again»;
- `/clear` между макрошагами;
- модель — Sonnet, Opus только где отмечено.

## Макрошаги: что сдать и чем проверить

Подшаги внутри макрошага = его задачи `Pn.m` по порядку; после каждого — коммит `тип(Pn.m): …`.
